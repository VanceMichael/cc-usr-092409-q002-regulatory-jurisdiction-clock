# 消费争议数据约定

系统只保存完成争议分析所需的去标识化事实。来源事件、分类口径、商家身份映射和报告修订分别维护版本，已发布报告引用固定的数据水位。接口错误使用稳定的机器可读代码，所有持久状态进入同一 SQLite 文件。

## 管辖裁定与期限账本（跨省时）

跨省消费争议进入监管协同时，案件会因商家主体、消费者常住地或交易发生地变化而移交主办机构；补正材料、等待外部裁决会暂停法定期限，恢复后续计，紧急情况下可依法延长。系统不再依赖人工表格，而是以追加账本和单一责任链回答“谁在办、还剩多少时间、哪些时间被排除、材料签收没有、每次催办依据什么”。

### 基础数据

- `regions`：地区及固定 IANA 时区。计时始终换算为各地区当地墙钟时间，避免跨省错算。
- `calendar_days`：逐日工作日覆盖。默认周一至周五；法定节假日置 `nonworking`、调休上班置 `working`。
- `agencies` / `personnel`：机构隶属地区；人员通过 `personnel_region_grants` 获得对某地区的管辖授权，通过 `case_conflicts` 登记对某案的利益冲突。
- `rule_versions`：规则版本，正文为 `{stage_working_days, emergency_extension_max_days}`。正文一经发布不可原地修改（数据库触发器拦截），调整只能换版。

### 案件与证据水位

立案（`cases`）时记录商家主体地、消费者常住地、交易发生地、各方主张（`party_claims`）、适用规则版本，并立即开启首个法定期限阶段（`case_stages`）。

证据统一落在 `case_materials`，案件内以单调递增的 `seq` 作为证据水位；裁定与决定均记录当时水位。材料到达按 `(case_id, idempotency_key)` 幂等，重复提交不抬升水位。

### 管辖裁定

`jurisdiction_rulings` 只追加。确认主办/协办机构的人员必须同时满足：账户启用、被授权主办机构所在地区、对本案无利益冲突；否则返回 `jurisdiction_not_authorized` / `conflict_of_interest`。裁定留存证据水位与规则版本，并在同一事务内关闭旧责任链、开启新链。

`responsibility_links` 是责任链，部分唯一索引保证任一时刻每案只有一条 `effective_to IS NULL` 的有效链。受理时插入一条 `intake` 临时代管链，首条裁定或移交生效后关闭。

### 期限账本与计时

`deadline_events` 是只追加账本，事件类型：`open`、`supplement_request`（补正）、`wait_external`（等待外部裁决）、`resume`（恢复办理）、`emergency_extension`（紧急延长）、`close`（决定出具）。事件必须满足状态机（未暂停不能恢复、暂停中不能再暂停、时间不倒置），追加按 `(stage_id, idempotency_key)` 幂等。

计时引擎（`src/domain/clock.ts`，纯函数）按事件流切出计时/暂停区间，再与责任链求交得到地区切片：

- 一个工作日按 480 分钟计，日内按比例积分，因此开始当日即从开始时刻计；
- 暂停区间整段排除，并随快照给出 `reason_code` 与 `legal_basis` 作为暂停依据；
- 地区切片各用当地工作日历，逐日返回是否计期及分钟数（含节假日/调休、非工作日解释）；
- 紧急延长只追加预算，不改写已发生计时，累计受版本上限约束；
- 仅“正在计时”时外推预计到期时刻；暂停中不出具到期时刻；`close` 后时钟停止，之后永不计期。

### 决定不可改写

`decisions` 只追加，出具时钉选规则版本、阶段工作日预算，并固化当时时钟快照。数据库触发器阻止对决定、账本事件的 UPDATE/DELETE，并阻止修改阶段钉选的版本与预算。后来规则换版只影响之后开启的阶段，已出具决定的阶段永不被回溯改写。

### 移交原子协议

`transfers` 状态机：`proposed → frozen → received/effective →（或 cancelled）`。

1. 仅当前主办机构可发起；部分唯一索引保证同案同时只有一条在途移交，并发发起只保留一条。
2. 交出方 `freeze`：对当时已归属材料生成规范 JSON 的 SHA-256 清单并冻结版本；此后到达的材料不进水位，落入待归属区（`pending_attribution`，并永久记录 `arrived_during_transfer_id`）。
3. 接收方 `receive`：签收人必须隶属接收机构，且提交的 `manifest_hash` 必须与冻结版本完全一致，否则 `manifest_version_mismatch`。签收、关闭旧链、开启接收方新链、移交置为 `effective` 在同一事务内原子完成。
4. 重复签收按幂等键返回原收据、不新增链路；同键不同版本判为冲突。
5. 在途移交期间禁止插入新的管辖裁定，避免责任链分叉。
6. 交出方可在签收前 `cancel`；冻结期间挂起的材料恢复正常签收并补取连续水位。
7. 待归属材料由新主办 `attribute`（认领，补取水位）或拒收。

### 到期扫描与持久通知

扫描器（`src/scanner.ts`）在进程启动时立即执行，并按 `SCANNER_INTERVAL_MS`（默认 60 秒）持续运行。对每个未决阶段重算时钟：剩余不足两个工作日写一条 `due_soon`；预算用尽仍在计时按当地自然日写 `overdue`；暂停中不报警。

通知（`notifications`）全部持久化，以 `dedup_key` 去重（阶段级临期、阶段+自然日级逾期、案件+催办键）。因此进程重启后扫描自然续跑，且不会对同一事项重复打扰；每条通知的 `basis_json` 固化当时负责机构、时钟数字、被排除时间段与待归属材料，即“每次催办的实际依据”。

### 任一时点回放

`GET /cases/:id/timeline?as_of=…` 只读取追加账本，返回该时点：

- 当时负责机构（责任链按 `effective_from/effective_to` 回放）；
- 各阶段当时状态、剩余时限、预计到期、被排除时间段及暂停依据；
- 截至当时仍未签收（待归属）的材料及其在途移交；
- 当时已发生的主张、裁定、移交（含当时状态与冻结清单）、决定；
- 截至当时的每一条通知/催办及其依据。

所有时间戳以 UTC ISO-8601 存储，日期口径为地区当地 `YYYY-MM-DD`。写接口普遍要求 `idempotency_key`，错误统一为 `{error:{code,message,details}}`。
